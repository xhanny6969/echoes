              [TECHNICAL_DOCUMENTATION_&_FAQ]
            

            

              Frequently Asked Questions (Architecture & Security)
            

            

              Deep-dive technical specifications on how Echoes enforces deterministic on-chain spending boundaries on NEAR Protocol, why native access keys alone aren't enough, and how Hackathon Judges can verify the live vault.
            

          


          
          

            

              
              /
            

          

        


        
        

          
          
          
          
        


        
        

          
          
          

            
            

              

                At the NEAR protocol level, a FunctionCall access key carries two critical properties: (1) its native allowance (e.g., 0.25 NEAR) strictly meters execution gas fees, not outbound value transfers; and (2) protocol rules prohibit a FunctionCall key from signing transactions with a non-zero attached_deposit.
              

              

                Therefore, an autonomous agent using a scoped FunctionCall key cannot directly attach NEAR tokens to pay external APIs or compute providers. Echoes bridges this architectural gap: the agent invokes spend_as with 0 attached_deposit, and the Echoes Rust Vault contract enforces stateful accounting (per-transaction limits, cumulative agent caps, global vault ceiling, and recipient allowlists) before executing Promise::new(recipient).transfer(amount) from the vault's treasury.
              

            

          


          
          

            
            

              

                Every guardrail in spend_as is enforced before any transfer is scheduled. When a check fails the contract traps (Rust fail() → unreachable), so the whole receipt reverts: no Promise::transfer is ever created, spent_today is not incremented, no log entry is written, and zero yoctoNEAR moves. A prompt-injected agent therefore learns nothing and gains nothing per attempt — every retry costs it gas and fails identically.
              

              

                Reverting alone would let a compromised key keep retrying forever, so Echoes adds an explicit owner-controlled kill path: revoke_agent(agent_id) flips active = false in persistent storage, and reactivate_agent / set_paused are gated by assert_owner(). Both are verifiable on this testnet account: revoke_agent and reactivate_agent transactions are listed below with block-level receipts.
              

              

                Note: revocation is owner-triggered, not automatic. We deliberately did not market an "auto-revoke on breach" primitive — a contract cannot safely self-disable a key on a reverted receipt, and doing so non-atomically would require a separate keeper.
              

            

          


          
          

            
            

              
Every spend_as(agent_id, recipient, amount) call traverses five sequential verification gates:

              
    
                
  1. GATE 01 (Protocol Key Scope & Predecessor): NEAR Runtime validates the ed25519 key is restricted to spend / spend_as with gas ≤ 0.25 NEAR.
    2. 
                
  2. GATE 02 (Circuit Breaker): Asserts the vault is not paused by the owner (!self.is_paused).
    3. 
                
  3. GATE 03 (Agent Active Status): Confirms the agent exists and agent.is_active == true.
    4. 
                
  4. GATE 04 (Recipient Allowlist): Confirms self.allowlist.contains(&recipient). Otherwise the call reverts before any transfer is scheduled.
    5. 
                
  5. GATE 05 (Dual Velocity Caps): Enforces three arithmetic ceilings simultaneously: amount <= agent.per_tx (0.20 Ⓝ), agent.spent_today + amount <= agent.daily (1.00 Ⓝ), amount <= vault.per_tx (0.50 Ⓝ), and vault.spent_today + amount <= vault.daily (5.00 Ⓝ).
    6. 
              

            

          


          
          

            
            

              

                Administrative methods (reactivate_agent, set_paused, add_to_allowlist, and register_agent) are protected by two independent barriers:
              

              

                First, at the NEAR Runtime level, each agent's FunctionCall access key explicitly whitelists only ["spend", "spend_as"]. Any transaction signed by an agent key attempting to invoke reactivate_agent or set_paused is rejected by NEAR validators before WASM execution even begins (demonstrated in Preset 05). Second, inside the contract, assert_owner() verifies env::predecessor_account_id() == self.owner_id.
              

            

          


          
          

            
            

              

                On NEAR Protocol, transaction nonces are tracked per AccessKey rather than per account. By provisioning a dedicated ed25519 FunctionCall Access Key for each autonomous worker in the swarm (agent-alpha, agent-beta), multiple agents can sign and broadcast transactions concurrently in the same block with zero nonce contention—while the Echoes contract atomically serializes their cumulative deductions against the shared Global Vault Cap.
